# 0006 新增硬约束 #9：每个公开开关必须有产物级断言（翻转 ⇒ 变红）

## 背景

本项目在 P1 / P2 清剿中反复踩同一类雷：**防御开关 / 公开能力开关存在，但没有"翻转它会红"的断言**。
典型如 `setDevMode()`（P2-5，实测开关有效但缺断言）、bundler / compat 的预设开关、SSR / hydration 标记、
各 `process.env` 编译期常量。这些开关一旦被悄悄改坏（或根本没生效），CI 全绿却线上行为漂移——违背硬约束 #2（全绿 ≠ 可用）。

本仓已用"注入缺陷验证门禁会红"的纪律（硬约束 #2 / #8）堵住了"改门禁脚本"这一类；
但**开关本身的产物级断言**还没有成文硬约束，只能靠各 PR 自觉。

## 决定

**新增硬约束 #9：每个公开开关 / 防御开关必须有产物级断言——翻转该开关必须让对应测试变红（注入式验证）；无断言的开关不得合并。**

- "公开开关"指：编译期常量（`__DEV__` / `process.env.*`）、预设 / 模式选择（`preset` / `ssr` / `scoped`）、
  运行时能力开关（`setDevMode` 等）、以及任何"开了 / 关了行为不同"的公开 API。
- "产物级断言"指：**真跑一次**——把开关翻到另一端，断言失败（红）；而非 grep / `--dry` / 文档声明。
- 验证手段沿硬约束 #8：运行时导出面探针（`await import(dist)` + `Object.keys()`）+ 真实行为断言（mount / 渲染 / 求值）。

## 被否掉的选项

| 选项 | 为什么没选 |
|---|---|
| 只在 review 清单里口头要求 | 不可判死——硬约束 #8 的注释明确"写不出检查方式的不是硬约束，是愿望"；必须成文且可门禁化 |
| 要求每个开关都补单测即可 | 单测测"现在的行为"，不保证"翻转会红"——无法发现开关被悄悄禁用（P2-5 即此病例） |
| 用静态分析扫描开关 | 开关形态太多（常量 / 预设 / 运行时），静态扫不全；产物级断言才是真结论 |

## 后果

- 好处：开关类回归被机械捕获；与硬约束 #2（全绿 ≠ 可用）、#8（核实打到被验证对象）形成闭环。
- 代价：新增公开开关须多写一条"翻转 ⇒ 红"的断言；存量开关需补（棘轮，不一次性追平，登记原因）。
