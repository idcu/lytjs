# 0014 体积/性能取舍必须先用实测盈亏平衡点支撑

## 背景

B01b 把优化版的三类体积手法移植到基础实现。其中「短别名」在批准时只有**推断**：
单模板省 78 B（去首行映射后的反事实）、编译器固定成本 +431 B，被当作「模板数够多就能回本」。
批末用同口径实测（esbuild bundle + gzip，同一源码只删别名机制）推翻了该推断：

- 100 模板语料：别名 65,052 B vs 全名 58,797 B（**+6,255 B，100/100 模板都更大**）；
- 50 个同族模板 N=1/5/20/50：gzip 分别 +179/+182/+191/+180，**不随 N 收敛**；
- raw 平衡点≈6 个模板只在「去掉首行调试映射」的反事实口径下成立，gzip 口径 50 个仍未回本。

按引用裁剪 import（−7,688 B）才是那 10% 收益的真实来源，与别名机制无关。

## 决定

1. **回退**短别名机制：别名表、字符串感知替换、产物首行 `//lytjs-signal:` 映射、
   `signal-renderer.ts` 的参数缩短契约；**保留**按引用裁剪 import。
2. 保留项 2（静态 HTML 复用）、项 3（单插值复用）、项 4（v-memo 守卫）。
3. 今后体积/性能取舍：必须先在同口径（真实依赖、esbuild bundle + gzip、可复算脚本）做 A/B
   实测并给出盈亏平衡点，**才允许批准**；推断、局部 raw 数字、单模板收益不得作为批准依据。

## 被否掉的选项

| 选项 | 为什么没选 |
|---|---|
| 保留别名，只把首行映射改为短来源注释 | 映射是调试可追溯契约的一部分；去掉后 gzip 口径 50 模板仍不回本（+100） |
| 等模板数增长到回本 | N=1→50 的 gzip 差值不收敛（+179…+191），大语料反而更差 |
| 连「按引用裁剪 import」一起回退 | 它是 −7,688 B 的真实来源，属独立机制 |

## 后果

- 好处：主路径不再携带净负收益；产物回到全名，`SignalRenderer` 契约断链风险降低且可读。
- 代价：单模板文本略长（未压缩时）；已接受的调试映射仅作为历史记录保留在坑库与评估文档。

## 判据

- 100 模板基础产物 raw = **58,797 B**（复算见 `evaluation/LYTJS_体积归因_2026-11-06.md` §9.3）；
- `node scripts/check-compiler-parity.mjs`：77/100、`expectedMismatch` 0、vnode/SSR 快照逐字一致；
- `tsx scripts/check-bundle-size.ts --verbose`：minimal-app **92,538 B**（回退 −179 B）。
